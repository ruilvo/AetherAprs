# R6.6 audit: what landed, what did not

Date: 2026-11-27. Baseline commit `71b3e29` (merge of the R6.6 transport work).

This document records an audit of the R6.6 roadmap row against the shipped code, and
of two cross-cutting questions raised at the same time (callsign versus addressee, and
use of `Stateless` for state machines). It exists so a later session can act on the
findings without repeating the investigation.

The audit's verdict: **R6.6 was reported complete and is not.** Six clauses of the row
are unimplemented or unreachable. Three of them were missed because the unit tests
build their own inputs instead of driving the real producers.

---

## 1. How the gap was missed

`AetherAprs.Tests/Android/AudioTransmitGateTests.cs` and
`AetherAprs.Tests/Android/AudioWriteLoopTests.cs` pass 30 green tests by
hand-constructing `AudioRouteSnapshot` values. They verify the gate's *logic* in
isolation. Nothing in the product ever constructs a snapshot or assigns it to
`AudioPlaybackService.RouteSnapshot`, so the gate is a permanent pass-through in the
shipped application.

The earlier conclusion "every acceptance bullet is covered by named tests" came from
reading test names rather than tracing call sites. **When auditing a row like this,
grep for the production writer of each input the tests fabricate.** A test that builds
its own input proves the consumer works, never that anything delivers that input.

## 3. Confirmed gaps — work items

The roadmap now carries these as R6.9 to R6.12. Each section below is the detail a
future session needs.

### 3.1 R6.9 — AFSK cannot be created or edited in the UI

**Impact:** the largest item. An entire port type is unreachable.

`AfskSettings` (`Configuration/PortConfig.cs:274`) is a first-class
`IPortTypeSettings` with a complete implementation behind it:

- registered as a JSON derived type (`PortConfig.cs:102`)
- persisted via `AfskSettingsRecord` (`Data/Entities/PortRecord.cs`) and mapped in
  `Data/Mappers/PortRecordMapper.cs:75-90` (write) and `:155-163` (read)
- has its own migration (`20261120174406_AddAfskSettingsToPorts`,
  `20261120184812_AddAfskChannelAccessToPorts`)
- built by `ModemFactory.CreateAfskModem` (`Services/Ports/ModemFactory.cs:126-135`)
- validated by 15 tests in `AetherAprs.Tests/Configuration/AfskSettingsTests.cs`

and no UI can create it:

- `AddEditPortViewModel.cs:160` — `public Type[] PortTypes { get; } = [typeof(AprsIsSettings), typeof(KissSettings)];`
- `AddEditPortPage.axaml` — no section mentions AFSK; the two visible sections are
  guarded at lines 102-104 (APRS-IS) and 139-141 (KISS)
- `Converters/UI/EnumDisplayConverter.cs` — maps only `AprsIsSettings` and
  `KissSettings`, in both `Convert` and `ConvertBack`
- `ViewModels/Components/PortItemViewModel.cs:28-33` — `TypeName` falls through to
  `PortTypeUnknown` for a stored AFSK port

**Settings to expose** (all on `AfskSettings`, all persisted, none present in the
ViewModel or page — verified 0 of 7):

| Property | `PortConfig.cs` line | Default | Constraint |
|---|---|---|---|
| `PttMode` | 295 | `PttMode.None` (VOX) | enum, validated by `Enum.IsDefined` |
| `TxDelayMs` | 313 | 300 | non-negative |
| `TxTailMs` | 331 | 50 | non-negative |
| `SlotTimeMs` | 350 | 100 | non-negative |
| `Persist` | 368 | 63 | 0-255 |
| `AudioLevel` | 385 | 0.9 | open interval (0,1) |
| `SquelchThreshold` | 404 | 0.1 | closed interval [0,1] |

**Work:**

1. Add `typeof(AfskSettings)` to `PortTypes`.
2. Add both directions of the type mapping to `EnumDisplayConverter` with a new
   `PortTypeAfsk` key in all 8 resx.
3. Add `AfskSettings` to the `TypeName` switch in `PortItemViewModel`.
4. Add an AFSK section to `AddEditPortPage.axaml` following the existing APRS-IS / KISS
   pattern: a `StackPanel` gated by
   `{StaticResource TypeNameToIsVisibleConverter}` with
   `ConverterParameter=AfskSettings`.
5. Add the seven properties to `AddEditPortViewModel`, populate them in
   `Initialize` (see the existing `config.TypeSettings switch` at line 546), and write
   them in `BuildConfig` (line 743; the APRS-IS and KISS branches are at 754 and 770).
6. Add validation mirroring `AfskSettingsTests` so the editor rejects out-of-range
   values before save, in the same style as `ValidateAsync`.
7. Add a save/reload round-trip test for the editor.

**Design question to decide, not assume:** the row says "separate VOX from physical PTT
capability". Today `PttMode` has exactly two members (`PortConfig.cs:262`):
`None = 0` documented as "No PTT control; the radio keys itself (VOX)" and
`SpeakerMic = 1`. That conflates "no PTT control" with "VOX" and offers no way to
express what the device is actually capable of. `IPttService`
(`Services/Platform/IPttService.cs`) is only `Engage`/`Release` with no capability
query, so a port cannot ask whether physical PTT exists before offering the option.
Adding a `SupportsPtt`-style capability to `IPttService` and splitting the enum is the
honest fix; picking one arbitrarily is not.

### 3.2 R6.10 — audio route and focus are never wired

`AetherAprs.Android/Services/Platform/AudioRouteValidator.cs` defines
`AudioRouteSnapshot(Route, IsFocusGranted, IsBecomingNoisy, Generation)` and a
generation-bound `AudioRouteValidator` with `Authorize` / `Revalidate`. The logic is
correct and tested. Nothing supplies it:

- `AudioRouteSnapshot` is constructed at exactly one site: its own declaration
  (`AudioRouteValidator.cs:40`). No `new AudioRouteSnapshot` anywhere.
- `AudioPlaybackService.RouteSnapshot` (`:28`) is declared and read (`:43`, `:81`) but
  **never assigned**.
- `AetherAprs.Android` contains no `RequestAudioFocus`, `AbandonAudioFocus`,
  `AudioDeviceCallback`, `AudioManager.Mode` observation or
  `ACTION_AUDIO_BECOMING_NOISY` receiver. So `IsFocusGranted`, `IsBecomingNoisy` and
  `Generation` have no platform source; generation never advances and a headset
  unplug is never observed.
- `AfskModem.cs:166` keys the radio with `_ptt.Engage()` — the unconditional public
  method — not `PttService.TryEngage(snapshot)`. `TryEngage` (`PttService.cs:49`) and
  `CheckBeforeTransmit` (`AetherAprs.Android/Services/Platform/AudioTransmitGate.cs:100`)
  are `internal` and reachable only
  from the two Android services themselves, so the core modem cannot use them at all.

**Work:**

1. Decide where the snapshot is produced. The natural owner is the Android layer that
   can observe `AudioManager`: an `AudioRouteProvider` that registers an
   `AudioDeviceCallback`, requests focus for the transmit duration, and raises
   `BECOMING_NOISY`, incrementing `Generation` on every route change.
2. Add a route/focus capability to the platform abstraction seam so `AfskModem` can
   obtain a snapshot without referencing Android. `IPttService` is the existing seam
   and currently has no snapshot concept.
3. Assign `AudioPlaybackService.RouteSnapshot` before playback, or replace the mutable
   property with a provided lookup — a settable property that nobody sets is how this
   defect survived review.
4. Route AFSK transmit through the checked key path.
5. Write the regression test against the **real producer**. A test that constructs
   `new AudioRouteSnapshot(...)` reproduces the existing blind spot.

### 3.3 R6.11 — connection reporting gaps

Three separate problems, all in the "reconnect outcome" and "GATT
service/characteristics" clauses.

**a. Negotiated service and characteristics are captured but never rendered.**
`KissBluetoothLeDetail` carries `ServiceUuid`, `RxCharacteristicUuid`,
`TxCharacteristicUuid` (`KissConnectionProgress.cs:136-143`). `DescribeDetail`
(`KissConnectionStatusText.cs:53-96`) reads only `PayloadSize`, `AttMtu`, `WriteMode`
and `NotificationsEnabled`. Grep for the three UUID names in that file returns
nothing. The operator never sees which service the link actually used — which is
exactly what matters when the LilyGO profile auto-detection picks the non-default
profile.

**b. Reconnect outcome is structurally unreachable.** `KissConnectionProgress.Attempt`
is documented as "A value above one means the session is reconnecting after an
earlier attempt failed" (`:162-165`), and `DescribeDetail` renders
`ConnectionDetailAttempt` only inside `if (progress.Attempt > 1)` (`:88-91`). But
`PortSessionManager.CreateModemAsync` hardcodes `Attempt: 1` on every connect
(`PortSessionManager.cs:361`) and builds a fresh `KissConnectionProgressRecorder` per
attempt, so `Attempt` is always 1 and that branch never runs.

Retry counting does exist, one layer up: `SessionCoordinator.ReconnectLoopAsync`
(`SessionCoordinator.cs:461-513`) counts `retryCount`, applies exponential backoff
with jitter (`CalculateBackoff`, `:515-524`) between
`DefaultInitialBackoff` (1s) and `DefaultMaximumBackoff` (5min), and records
`RetryCount` / `NextRetryUtc` / `Error` into `PortSessionStatus`
(`SessionCoordinator.cs:29-44`). None of that reaches `KissConnectionProgress`.

**c. The port list reports intent, not state.** `PortItemViewModel.StatusText` is
`IsEnabled ? Strings.Get("Running") : Strings.Get("Stopped")`
(`ViewModels/Components/PortItemViewModel.cs:35-37`) — the operator's toggle, not the
session. A port sitting in a five-minute backoff still reads "Running". `RetryCount`
and `NextRetryUtc` are rendered nowhere in any view (verified across all `.axaml`);
they reach the operator only through `RedactedSupportReportService`.

**Work:** pass the attempt counter from `SessionCoordinator`'s retry loop down into
`KissConnectionContext`; render the UUIDs in `DescribeDetail` (add a key such as
`ConnectionDetailGattService`); project `PortSessionStatus` state plus
`RetryCount`/`NextRetryUtc` into `PortItemViewModel` so the list can distinguish
connected, degraded and waiting-to-retry.

### 3.4 R6.12 — messaging peer identity splits after a restart

**This is a correctness bug with operator-visible effect, and the smallest of the
four.**

`PacketRecordMapper` stores a missing SSID as `AprsSsid.PrimaryStation` because the
column is a required byte (`Data/Mappers/PacketRecordMapper.cs:82-85`):

```csharp
SourceSsid = packet.Source.Ssid.HasValue
    ? (AprsSsid)packet.Source.Ssid.Value
    : AprsSsid.PrimaryStation,
```

On reload, `MessageService` rebuilds the peer by round-tripping through `Callsign`
(`Services/Messaging/MessageService.cs:1141`):

```csharp
AprsAddress source = AprsAddress.FromCallsign(new Callsign(record.SourceBase, (int)record.SourceSsid));
```

`new Callsign("N0CALL", 0)` has `Ssid = 0`, and `AprsAddress.FromCallsign` copies it,
so the restored peer has `Ssid = 0`. The live path builds the peer differently — from
the parsed `Callsign`, whose parser normalises SSID 0 to null
(`Modems/Aprs/Ax25Parser.cs:135`): `AprsAddress.FromCallsign(message.Source)` at
`MessageService.cs:531` and `:593` yields `Ssid = null`.

`AprsAddress` is a `readonly record struct`, so `Ssid = 0` and `Ssid = null` are
**not equal**, yet `ToString()` renders both as `N0CALL` because it only emits the
suffix for `Ssid > 0`.

Consequences:

1. After a restart, each SSID-less peer's conversation is split in two:
   `_conversationList` lookups use `c.Peer.Equals(peer)` (`:946`, `:995`, `:1035`)
   and the reload merges by `peer.ToString()` (`AddToThread`, `:1313-1326`, key at
   `:1318`). A restored conversation and a newly received message become two threads
   that display the same name.
2. An incoming ACK for a message that was pending across the restart is **dropped**.
   The guard at `:601` compares `cached.Peer.Equals(peer)`; the restored `cached.Peer`
   has `Ssid = 0`, the incoming `peer` has `Ssid = null`, so it logs "Ignoring
   ACK/REJ …" and returns. The retry timer then expires the message even though the
   peer acknowledged it.

**Fix:** use the stored-aware factory on the restore path, as the addressee path
already does one line below:

```csharp
AprsAddress source = AprsAddress.FromStored(record.SourceBase, (int)record.SourceSsid);
```

`AprsAddress.FromStored` (`Models/Aprs/AprsAddress.cs`) already normalises a stored 0
to null and documents exactly this hazard. The same treatment is already applied to
the addressee at `MessageService.cs:1142` and in
`Data/Messaging/OutboxMessageStore.cs:361`.

**Regression test:** reload from the database and assert one thread per peer, plus an
ACK accepted for a restored pending message. Note the existing restart tests
(`AetherAprs.Tests/Services/Messaging/MessageServiceTests.cs:131`,
`:1086`, `:1154`) use a peer with an explicit SSID (`N0CALL-1`) in one case and a
`K0OTH` peer in the other, which is why neither catches this — assert on a
**SSID-less** peer specifically.

## 4. Callsign versus addressee — verdict: the model is right, one call site is wrong

The separation is deliberate, documented and correctly typed:

- `Models/Aprs/Callsign.cs` — strict AX.25 station identity: 2-6 ASCII alphanumerics
  plus optional SSID 0-15. Also carries `HasBeenRepeated` for path entries.
- `Models/Aprs/AprsAddress.cs` — APRS message addressee: 1-9 characters including
  hyphens, because the APRS message field is nine arbitrary characters and tactical
  addresses such as `APRS2SOTA`, `EMAIL` and `NWS-` are valid recipients.

Usage honours the distinction:

- station fields (`Source`, `Destination`) are `Callsign` throughout
  `Models/Aprs/Packets/`
- message destination is `AprsAddress` — `MessagePacket.Addressee`,
  `MessageAckPacket.Addressee`, `MessageRejPacket.Addressee`, all three
- `ConversationThread.Peer`, `MessageService` peers, `BroadcastFailedException` paths
  and `ConversationDeepLink` all use `AprsAddress`, and `ConversationDeepLink` carries
  an explicit comment explaining why a `Callsign` would be wrong there
- the arrow back to a station identity
  (`AprsAddress.TryToCallsign`) exists and is used only where AX.25 genuinely requires
  it

**The one defect is `MessageService.cs:1141`**, covered in 3.4: it converts a stored
source through `Callsign` instead of `AprsAddress.FromStored`. That is both the wrong
direction (addressee-shaped data forced through the stricter station type, losing the
9-character tactical-address tolerance) and the cause of the SSID-0 identity split.

No other misuse was found. Do not "unify" the two types — the split is load-bearing.

## 5. Stateless for state machines — verdict: correctly applied

`Stateless` 5.21.0 is referenced once (`Directory.Packages.props`,
`AetherAprs/AetherAprs.csproj`) and used by exactly three types, matching the roadmap's
declared list:

| Type | States | Shape |
|---|---|---|
| `Models/Messaging/MessageDelivery.cs` | `Queued → Pending → Sending →` terminal | `Fire` / `TryFire` / `CanFire`, terminal states configured empty so they absorb |
| `Services/Ports/PortSession.cs` | `Stopped → Connecting → Connected \| Degraded` | same shape; `Stopped` deliberately does not accept `Faulted` |
| `Services/Transmission/BeaconQueue.cs` | `Queued → Sending → Sent \| Failed \| Expired \| Dropped` | same shape, four absorbing terminals |

The tables are stateless by design: `Fire(state, trigger)` builds the machine, fires and
returns the next state, because the caller already persists it. That is deliberate and
documented in each file.

The three adjacent non-machines are also deliberate and correct:

- `KeepAliveState` — a derived snapshot built through named factories
- `SessionLifecycleState` — an aggregate recomputed from the port set
  (`SessionCoordinator.UpdateAggregateStateLocked`, `:608-630`); it can legitimately
  jump between `Running` / `Degraded` / `Starting` as ports change, which is a
  function of the set, not a trigger sequence
- `AndroidLifecycleState` — mirrors what the OS reports; the platform owns the
  transitions

`AprsIsLoginStatus` and `PermissionGrantStatus` are value classifications with no
transition table, and are correctly not machines.

No change recommended.

## 6. Suggested order

Smallest and highest value first:

1. **R6.12** — one-line fix plus a real regression test; an operator-visible
   correctness bug.
2. **R6.11** — reporting only; no new platform surface.
3. **R6.10** — requires a platform snapshot producer, so it needs design decisions
   about where the Android seam lives.
4. **R6.9** — the largest; a new editor section, a type mapping, and the VOX/PTT
   capability question that should be settled first because it changes `IPttService`.

R6.6 itself is now device-only: Classic SPP discovery, BLE MTU negotiation and
chunked write, and audio route/focus loss mid-frame on real hardware.
